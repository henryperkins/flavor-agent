## Current capture paths and constraints

The repo already ships capture tooling — `npm run audit:screenshot`
(`scripts/browser-run-screenshot.js`), which drives the Cloudflare Browser
Rendering API and has `settings`, `admin`, `block-editor`, and `site-editor`
presets. That remote renderer cannot be pointed at the local Docker stack,
because Cloudflare renders the page from **its** network and
`http://127.0.0.1:8888` is not reachable from there. A local Playwright capture
produced the required content recommendation still on 2026-08-26; the remote
renderer remains useful only for publicly reachable hosts.

To use the remote Browser Rendering capture tool, all of the following must be
true at once:

- `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` are set.
- `BROWSER_RUN_DEFAULT_BASE_URL` points at a **publicly reachable** WordPress
  host running this plugin — a staging site or a tunnelled local stack.
- WordPress admin authentication is supplied via `--cookies-file`,
  `BROWSER_RUN_COOKIES_JSON`, or `--extra-headers-file`; every remaining asset
  is behind `/wp-admin/`.
- For every asset except `settings-readiness`, the staged site has working
  provider credentials in `Settings > Connectors`, because the surfaces render
  a real model response. The pattern asset additionally needs a populated
  pattern index.

The local Playwright capture did not require Cloudflare Browser Rendering. It
used the pinned WordPress 7.1 harness, installed the Anthropic connector, and
passed the ignored local key to the one CLI request as an environment variable;
the key was not persisted in WordPress.

## Honest characterisation of the gap

Five of seven stills remain optional/missing. The repository's minimum visual
gate is closed: `activity-audit.png` provides the governance-console proof, and
`content-recommendation.png` provides a real WordPress 7.1 native-editor result
from a fresh Anthropic-backed request. The latter is local harness evidence,
not a public staging-host capture; its environment, interaction, credential
boundary, browser health, and checksum are recorded in the linked validation
file.

The remaining five images would strengthen the public release presentation but
are not part of the repository's stated minimum of one governance-console image
plus one native-editor still.
