# UI / Theme / Style Review Contract

This document is the contract reference for evidence and coverage in Flavor Agent editor/admin UI audits.

Use it when you need to answer:

- Which mounted surfaces and shared seams belong in a requested UI audit?
- What evidence confirms a theme, style, accessibility, or stale-state issue?
- Which checks can resolve an uncertain finding without changing a live site?

Maintainers: keep this reference aligned with the UI/runtime owners and the review aids in `.codex/skills/ui-theme-style-review/`, `.claude/skills/ui-theme-style-review/`, and `.github/prompts/ui-theme-style-review.prompt.md`. Update the map when entrypoints, token contracts, apply paths, or admin interactions change. The current checkout governs behavior; this map is an inspection aid, not proof that every branch is mounted.

## Scope and coverage

Audit the requested UI and follow adjacent server/store code only far enough to establish its behavior. Read `review-response-protocol.md` for reporting and the relevant delta in `../prompts/surface-review-prompt.md` for a deeper surface contract. Historical review notes and `recommendation-ui-consistency.md` can explain intent, but current entrypoints and runtime guards decide reachability.

For a whole editor/admin audit, record coverage of each row below and the theme/style, accessibility, and stale-state checks applicable to it. A named-surface audit needs only its row and affected shared seams. A missing browser environment limits rendered claims; it does not prevent a source-confirmed finding.

All code paths in this document are relative to the repository root.

## Theme and style evidence

- **Keep the token layers distinct.** `src/tokens.css` defines intentional `--flavor-agent-*` brand extensions; standard UI consumes `--wpds-*`. Site content presets (`--wp--preset--*`, theme.json) describe another layer. A branded fixed palette or dimension is not itself a theming bug. Show a broken supported state, contrast failure, unresolved token, or concrete inconsistency with an enforced contract.
- **Resolve tokens where the UI lives.** Follow imports/enqueues and the cascade through the actual host, sidebar, portal container, or iframe document. `src/admin/wpds-runtime.css` imports public design tokens and bridges admin color-scheme variables; `src/admin/dataviews-runtime.css` imports DataViews styles. Do not assume editor runtime tokens exist on a standalone admin page or that root variables cross an iframe boundary.
- **Check compatibility against the checkout.** Read `package.json`, the lockfile, and installed package exports when available before relying on a token/component name, stylesheet path, or experimental/private API. Existing aliases, fallbacks, and wrappers may be deliberate. Flag an experimental call only when its active use causes a supported-runtime failure or violates a demonstrated compatibility contract; do not maintain a frozen allowlist of filenames.
- **Separate chrome from content.** Do not recommend injecting site theme.json styles into plugin chrome just because both use theme terminology. WordPress describes `@wordpress/theme` as the design-system package for application theming, separate from the site theme.json API. [WordPress theme package documentation](https://developer.wordpress.org/block-editor/reference-guides/packages/packages-theme/).
- **Measure a concrete combination.** Identify the element/state and winning foreground/background values; account for alpha, color-mix, gradients, parent surfaces, font size/weight, and active scheme. Literal colors and fallback values alone cannot establish a contrast failure. A source calculation is sufficient only when the winning combination is determinate; otherwise use computed styles and record the environment.
- **Check client/server contrast decisions together.** Compare `src/utils/style-operations.js` with `inc/LLM/StyleContrastValidator.php` using the same operations, preset resolution, inherited/effective scope, and baseline styles. Confirm an accepted/rejected or displayed-warning mismatch and its effect on review/apply; different helper implementations alone do not establish drift.

Prefer the available WPDS MCP for canonical components and semantic token roles. For Gutenberg/theme.json/REST/release questions, use the managed WordPress documentation search when available and inspect its primary URL and retrieval metadata. Corpus retrieval can include historical chunks; metadata alone does not establish compatibility with the installed release. Consult `developer-docs-public-corpus-runbook.md`, `inc/Cloudflare/AISearchClient.php`, and `inc/Support/DocsGroundingSourcePolicy.php` when source scope or currentness is material. Source labels are not freshness attestations; do not infer complete Plugin Handbook coverage.

## Accessibility and responsive evidence

Choose checks that match the scoped UI and observed hypothesis. Record the applicable WCAG criterion when claiming an AA failure; distinguish product motion preferences from a normative accessibility requirement.

- **Contrast and state communication:** normal text needs 4.5:1 and qualifying large text 3:1 under WCAG AA; required non-text control/state information generally needs 3:1 against adjacent colors, with criterion exceptions. Identify the applicable case and unrounded ratio. Status, errors, executable/advisory/stale distinctions, and approval states must remain understandable beyond hue. [Text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html).
- **Keyboard and focus:** verify accessible names, meaningful order, operable disclosures/actions, focus return, and visible focus on actual controls. Absence of a plugin-local `:focus-visible` selector is not evidence of failure: native/core styles or another focus treatment may provide it. Test clipping/overlay occlusion and cross-document focus routing, including the toast undo shortcut implemented in `src/components/ToastRegion.js`. [Visible focus](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html), [focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html).
- **Feedback and semantics:** loading, failure, validation, stale, and undo results need understandable labels and appropriate announcements. Inspect live-region/notice behavior, accordion expanded/control relationships, label/help/error associations, and icon-only controls. Confirm announcements with an accessibility tree or interaction evidence before claiming assistive-technology behavior.
- **Reflow and text scaling:** check narrow Inspector/Styles sidebars, small admin viewports, long translations, details panels, and Settings validation. Evaluate reflow at 320 CSS pixels and text enlargement to 200% where applicable; record actual viewport/panel width and scaling. Two-dimensional DataViews content can have reflow exceptions; surrounding controls and details still need usable access. [Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [text resizing](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html).
- **Motion and contrast preferences:** check `prefers-reduced-motion` across CSS and JS timers/animations, including paused toast lifetimes and restoration after hover/focus. Test supported dark/admin schemes and forced-colors where relevant to focus or state visibility. Do not declare dark-mode breakage without identifying a supported/active mode and the failing state.

Axe output, screenshots, a token scan, or a passing build can support specific observations; none certifies the whole UI. Name what was observed, what source establishes, and what remains untested.

## Freshness, apply, and capability evidence

Trace the actual lifecycle: request snapshot -> response acceptance -> display/review -> live preflight -> mutation/copy/insertion -> activity/undo. Resolve behavior separately for each owner; the UI does not give every surface the same execution model.

- **Freshness identity:** distinguish client request/context signatures, server `reviewContextSignature`, and `resolvedContextSignature`. Determine which the active path requires. Changes to target/entity/ref, selected block, live structure, theme config, capability/provider state, or resolved review context must not leave a previous result actionable when that context governs the action. A changed label or historical docs hash is not automatically applicability drift.
- **Async races:** inspect response ordering, abort/cancellation, remount/scope changes, retry state, and review closures. Demonstrate which obsolete result wins or which missing/stale signature still reaches an action; a disabled button alone does not prove every mutation path is guarded.
- **Editor applies:** start in `src/store/index.js` and `src/store/executable-surface-runtime.js`, then follow the relevant block/template/style action helpers and abilities. Confirm server revalidation where the path requires it, followed by the current local target check. Do not demand a server mutation endpoint for an intentionally local editor apply.
- **Advisory and editorial results:** check the permitted action instead of inventing one. Content copy has freshness semantics; embedded navigation is advisory; delegated chips are passive; pattern insertion has its own validation boundary. Confirm these distinctions against mounted code.
- **Capability and bridge behavior:** follow `src/utils/capability-flags.js`, `inc/Abilities/SurfaceCapabilities.php`, localization, and the visible unavailable/configuration state. Structured surface capability results take precedence when valid; legacy fallback is not automatically a defect. Trace `assets/abilities-bridge.js`, `assets/ability-execution-utils.js`, and `src/store/abilities-client.js` for readiness, abort signals, permitted REST fallback, and response normalization.
- **Activity and undo:** inspect `src/store/activity-session.js`, `src/store/activity-history.js`, `src/store/activity-undo.js`, `src/store/toasts.js`, `src/components/ToastRegion.js`, and `src/components/UndoToast.js` as relevant. Hydrated/fallback history must respect current scope and authorization. Undo must target the still-valid recorded state; test actual queue eviction, interaction pauses, focus routing, and failure persistence rather than assuming fixed queue constants.

## Admin-specific boundaries

- **Settings:** follow validation through rendering and controller state so urgent field errors do not disappear behind persisted collapsed sections. Check actual menu/capability/nonce and context-specific PHP escaping. Trace credential storage or providers only when the UI finding requires it; do not expose secrets in reports or browser artifacts.
- **DataViews:** open the imported API and custom detail renderer. Confirm search/filter/sort/per-page/pagination, persisted view validation, selected-row requests, and responsive details against the server contract. Do not claim DataForm or another component participates unless the opened runtime proves it.
- **Request logs:** `AiRequestLogPanel` lives inside `src/admin/activity-log.js`. Follow selected-row `ai/v1/logs/{id}` requests, partial/token-only/unavailable responses, stale response isolation, disclosure state, and administrator visibility. Compare Settings/core-log links and copy with `inc/Activity/RequestLoggingBridge.php` and current core logging, without widening the review into a general logging audit.
- **Pending external applies:** opening the detail can send `POST .../activity/{id}/claim`; leaving it may release the claim. Inspect selection/focus/visibility refreshes, conflict/expiration/terminal decisions, duplicate submissions, retries, and the correct row after a race. Connect visible controls to `inc/Apply/PendingApplyDecision.php` and its executor/permission checks; a capability-gated button does not establish server authorization or freshness. A review-only audit uses isolated fixtures for these interactions unless live mutation is authorized.
- **Attribution/discovery:** examine attestation and target links only when shown in the scoped UI. Confirm displayed status and unavailable/failed states from actual responses; do not equate a pending request, artifact link, local test, or unsigned result with a verified applied change.

## Verification routing

Read the nearest tests before deciding what to run. Targeted tests can settle a contract hypothesis or show a guarded regression; mock coverage alone cannot prove browser layout or deployed behavior. Report failures, unavailable prerequisites, and fixture limitations without converting them into unconfirmed product findings.

| Hypothesis | Nearest evidence to consider |
| --- | --- |
| Tokens/enqueues/standalone admin theming | `src/admin/__tests__/wpds-token-compatibility.test.js`, `tests/phpunit/ActivityPageTest.php`, `tests/phpunit/SettingsTest.php`; computed styles in the actual screen |
| Style validation/contrast/freshness | `src/utils/__tests__/style-operations.test.js`, `src/utils/__tests__/style-validation.test.js`, recommender and `src/style-surfaces/__tests__/` suites; `tests/phpunit/StyleContrastValidatorTest.php`, `tests/phpunit/StyleAbilitiesTest.php` |
| Template/block review and async state | Relevant recommender/helper suites, `src/inspector/__tests__/block-review-state.test.js`, `src/store/__tests__/executable-surface-runtime.test.js`, `src/store/__tests__/template-apply-state.test.js`; corresponding ability/controller tests |
| Toast/focus/undo/session behavior | `src/components/__tests__/ToastRegion.test.js`, `src/components/__tests__/UndoToast.test.js`, `src/store/__tests__/activity-undo.test.js`, activity-session/component suites; actual iframe keyboard flow |
| Settings/DataViews/logs/claims | `src/admin/__tests__/settings-page-controller.test.js`, `src/admin/__tests__/activity-log.test.js`, `src/admin/__tests__/activity-log-utils.test.js`, `src/admin/__tests__/activity-client-boundary.test.js`; `tests/phpunit/ActivityPermissionsTest.php`, `tests/phpunit/ApplyClaimTest.php`, `tests/phpunit/ExternalApplyLifecycleTest.php` |

Use `npm run test:unit -- --runInBand <nearest suite>` or `composer run test:php -- --filter <TestName>` when a run is useful. Browser evidence comes from the relevant Playwright test under `tests/e2e/` using the configured Playground or WP 7.0 harness; inspect the current config before choosing `npm run test:e2e:playground -- <spec>` or `npm run test:e2e:wp70 -- <spec>`. Follow `local-environment-setup.md` before treating another local installation as representative. A fixture suite is not live-provider or deployment proof.

An audit does not require a build/full verification run. Build only when confirming an asset/bundle hypothesis, in a suitable checkout, and record any resulting artifacts. If fixes are authorized later, use `cross-surface-validation-gates.md` for additive implementation/release checks and `npm run check:docs` for changed contracts/contributor docs. Do not silently waive a known-red or unavailable browser gate when reporting release readiness.
