### Strict run 1 (failed)

Strict run 1 at `c50e0e4` ran from 00:16:36 to 00:38:30 UTC and failed. Eight steps passed. The Site Editor step passed 46 of 47 cases.

The failing case was "dismissal requires an explicit click and keeps later apply available". It was the first Site Editor case after the harness's fresh install. The suggestion rendered, but the panel marked it stale with "Block or prompt changed", so the dismissal control never appeared. Summary SHA-256: `86db7552cb65ffa5d3f521d59628a36f43c34572153318ba9695e32f9d75b1ea`.

**Root cause.** The editor bundle is byte-identical to v0.1.1, so the race predates this candidate. Diagnostic reproductions captured each block request body:

- 8 warm runs and 4 restart-cold runs stayed fresh.
- All 3 fresh-install runs went stale. In each, the first request carried an empty `blockOperationContext.allowedPatterns`, the settled Refresh request carried 63 patterns, and every differing path was an allowed-pattern entry.
- Waiting for the catalog to hydrate before "Get Suggestions" kept 3 of 3 fresh installs fresh.

**Fix.** `ec2b9f9` adds that wait to the persistence helper, mirroring the smoke spec's helper of the same name. The committed helper then passed the real case after three separate fresh resets.

Two limits remain:

- The helper waits for a non-zero count. That is complete on a fresh site because no user patterns exist there. On a site that already has user patterns, the count could turn non-zero before the server catalog loads.
- The product race itself is unchanged and tracked in [current open work](../reference/current-open-work.md).

The original Playwright trace, screenshot and error context were lost when a later targeted run reused `output/playwright-wp70`. The step logs, `summary.json` and a dated notes file with the extracted page snapshot and network timeline were kept (notes SHA-256 `01ae237dcbec884f36c1bc4557abd6c0eb829891cda0c7c8c3369aac66e6677a`).
